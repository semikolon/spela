# spela — AI-Agent-Ready Media Controller

## NO PERSONAL DATA (MANDATORY)
**Public repo.** Never commit real names, IPs, API keys, device names, or household details to code/docs. Use placeholders. Runtime config (`config.toml`, `state.json`) is user-local and gitignored.

## Overview

Rust CLI + HTTP API server for torrent-to-Chromecast streaming. Single 5.2MB binary, zero runtime deps on target (ffmpeg only; BitTorrent client is embedded via librqbit since v3.3.0).

**Status**: v3.22 LIVE on Darwin (`darwin.home:7890`). Single Rust binary; ffmpeg the only runtime dep (BitTorrent embedded via librqbit).

**Current capabilities**: torrent → Chromecast / VLC / in-browser / Shannon streaming, driven by the web remote (`/remote`) + a thin CLI + a direct HTTP API. HLS transcode (HEVC→H.264 NVENC for Chromecast; HEVC pass-through for browsers; original-language audio — never a dub); **5-tier Sarpetorp-tuned ranker** (target-scoped codec preference); Smart Resume + per-episode HWM; self-healing disk cache; Local-Bypass of the on-disk library; alass subtitle-sync; source-racing on weak swarms; anti-poisoning blocklist. **Watch tracking (the TV-Time replacement)**: a unified `/home` queue (Continue → New Episodes → Coming Soon → Recommended; "Coming Soon" = caught-up followed shows with an upcoming TMDB `next_episode_to_air`, air-date-labelled), a followed-shows new-episode tracker with non-linear seen-seasons, the watch-ledger as the single source of truth for progress (survives unfollow), and an arsenal-and-harness recommender (Claude writes `recommendations.json`). **Open-in-VLC** with a web-remote control now-view relayed via the Mac-side `spela-vlc-bridge`. **VLC is the DEFAULT play target** (the Mac monitor is the main watch surface now); library titles open in VLC via the SAME shared target dispatch (`playToTarget`) as torrent plays (`/library/vlc.m3u` resolves a library title to its serve-library URL for native VLC decode).

**Graceful restart — LIVE (socket-activated, 2026-08-04).** systemd `spela.socket` holds both listeners (LAN IP + loopback, `FreeBind`) across a `spela.service` restart; spela inherits the fds via `listenfd` and stops accepting new connections on SIGTERM (`.with_graceful_shutdown`), so the socket stays bound the whole time and a redeploy no longer drops the port. **A LIVE stream is an effectively-infinite connection that cannot drain**, so a mid-watch restart waits out `TimeoutStopSec=10` then gets SIGKILLed — that is EXPECTED, not a bug (the journal's `stop-sigterm timed out, Killing` line is normal); RECONNECTION, not draining, is what carries a live stream across the ~1s gap. **Resume by stream type**: Chromecast auto-resumes via boot-resume (`maybe_resume_stream_on_boot` re-establishes transcode+cast from the persisted `CurrentStream`; Chromecast-scoped + recency-guarded + `SPELA_NO_RESUME` kill-switch); browser hls.js + VLC self-recover on reconnect — `handle_vlc_stream` re-resolves the result id from persisted `last_search` + re-adds the torrent ON-DEMAND (no `CurrentStream` needed), and the `vlc://` handler passes `--http-reconnect` so VLC resumes the byte-range from its last offset (spela serves Range). **So VLC is NOT the weak restart case — it self-heals.** Units live in the Darwin hemma overlay + `/etc` (`systemctl enable spela.socket`). **SPA served from disk** (`handle_remote_html` reads `CARGO_MANIFEST_DIR/static/remote.html`, embedded `include_str!` fallback) so a frontend edit goes live on the next Darwin `git pull` with NO `cargo build` or restart. **VLC reconnect-across-restart is verified live** (2026-08-04: after a real restart, VLC re-requested a mid-file byte-range and resumed in place — even on the pre-`--http-reconnect` handler, via VLC's own resume-on-disconnect). The one remaining owed live-verify is the Chromecast boot-resume path (a cast re-establishing itself across a restart).

**Operational detail lives in the Key Files + Hard-Won Lessons sections below; the current-vs-desired gotchas + the audio-drop root cause are in Hard-Won Lessons. Version-by-version history is in `git log` (each vX.Y maps to its commits) — this Status is deliberately NOT a changelog (that chronicling belongs in git, per the documentation philosophy).**

**Architecture**: `spela server` on Darwin (`darwin.home:7890`). `spela <command>` thin HTTP client from any LAN machine. Voice assistants call HTTP API directly.

## Usage

```bash
spela search "Good Luck Have Fun Dont Die"       # Auto-detects movie vs TV
spela search "legion" --season 1 --episode 5   # Search + rank results
spela play 1                                     # Play result #1 (auto: magnet, file_index, metadata)
spela play 1 --cast "Vardagsrum"                 # Play to living room TV
spela play 1 --no-intro                          # Skip intro bumper
spela next                                       # Next episode
spela pause / resume / stop                      # Playback control
spela status / history / targets                 # Info
```

`spela play <N>` is the primary flow. Carries all metadata (file_index, IMDB, show, season, episode) automatically from the last search.

## Build & Deploy

```bash
# Repo cloned on Darwin at ~/Projects/spela (Rust 1.94):
cd ~/Projects/spela && git push   # from Mac
ssh darwin 'cd ~/Projects/spela && git pull && nice -n19 cargo build --release'   # nice: see ⚠ below
ssh darwin 'sudo systemctl restart spela'
```

**⚠ ALWAYS low-priority the Darwin `cargo build` — it shares 4 cores with latency-sensitive services (2026-07-29 rule).** Darwin co-hosts the **single-slot `llama-embeddings` server** (`192.168.4.1:8080`, `--embedding`, NO `--parallel` — it serializes ALL consumers: mannaminne semantic search, Ruby, Graphiti) plus Graphiti-SSE (:8500), AdGuard DNS, and the router. A full `cargo build --release` spikes the 4-core box to load ~7 and starves them — a spela rebuild on 2026-07-29 timed out mannaminne's semantic layer for ~an hour. So `nice -n19 cargo build --release` (above) or `systemd-run --scope -p CPUWeight=idle cargo build --release`. Belt-and-suspenders on the embedder side: a systemd drop-in gives it `Nice=-10`/`CPUWeight=10000` (dotfiles `f424ee83`), but nice-ing the build is the courtesy that keeps DNS/embedder tail-latency clean. (An in-flight *transcode* is unaffected by a build — segments serve from disk — but the EMBEDDER is, so nice the build regardless of whether a stream is live.)

`~/.local/bin/spela` on Darwin is a symlink to `~/Projects/spela/target/release/spela` (verified Apr 30, 2026 — `lrwxrwxrwx ... -> /home/fredrik/Projects/spela/target/release/spela`). `cargo build --release` rewrites the inode the symlink points at; the running spela process keeps the OLD inode open until `systemctl restart` re-execs against the symlink. **No `cp` step needed** — earlier versions of this doc had `cp ~/Projects/spela/target/release/spela ~/.local/bin/` which errors with "are the same file" (Apr 30 deploy hit this).

**Build while the user is watching — compile freely, HOLD the restart (2026-07-04 operational rule)**: because the running spela keeps the OLD inode until `systemctl restart`, you can `git pull && cargo build --release` new code on Darwin *while a stream is live* with **zero interruption** — the build only stages the new binary at `target/release/spela`; nothing swaps into the running process until a restart. So during an active watch: **write + compile + commit freely; NEVER `systemctl restart spela`** (that kills the live cast) until the user confirms they're done watching. Any verification that needs a restart + a test-cast (e.g. the intro-warmup swap, or any cast-path change) waits for the user. A `cargo build` briefly competes for CPU with an in-flight transcode, but the transcode races ahead of playback and segments serve from disk, so the live stream is unaffected — BUT `nice -n19` the build regardless (MANDATORY for the co-hosted single-slot embedder, see the ⚠ above — not just paranoia). This makes "do unattended spela coding while I watch something" a first-class workflow — the only gated step is the restart-and-verify at the end.

**Running a SECOND isolated test instance on Darwin (test streams without touching production)** — for unattended barrage/latency/health testing while production (7890/Vardagsrum) stays live. Launch:
```bash
source ~/.secrets/tier-servers.env   # 2026-07-14: TMDB_API_KEY + MDBLIST_API_KEY now come from the age-encrypted tier-servers, sourced in prod's unit ExecStart (canonical fleet pattern, cf. sluss-web) — NOT inline Environment= anymore
SPELA_STATE_DIR=/home/fredrik/.spela-test SPELA_MEDIA_DIR=/home/fredrik/media-test SPELA_EPHEMERAL_DHT=1 TMDB_API_KEY=$TMDB_API_KEY MDBLIST_API_KEY=$MDBLIST_API_KEY \
  setsid /home/fredrik/Projects/spela/target/release/spela server --host 192.168.4.1 --port 7891 > /tmp/spela-test.log 2>&1 < /dev/null &
```
Four collisions the env-flags avoid (each cost a failed launch when discovering this): **(1)** `SPELA_EPHEMERAL_DHT=1` — the persistent DHT reloads its stored `listen_addr` from the shared `~/.cache/com.rqbit.dht/dht.json` and tries to bind production's UDP port ("librqbit engine bootstrap failed"). This flag keeps DHT ON but skips persistence → librqbit binds an ephemeral OS-assigned port → REAL peer discovery, zero collision. (Do NOT use `SPELA_DISABLE_DHT` for latency testing — trackers-only starves peer discovery: an 859-seed torrent saw 1 peer at t=3s, inflating every measurement.) **(2)** `--port 7891` — the CLI `--port` (main.rs, default 7890) OVERRIDES `config.port`, so the `SPELA_PORT` env is dead; the loopback dual-bind also keys off it, else it fights prod's `127.0.0.1:7890`. **(3)** `SPELA_STATE_DIR`/`SPELA_MEDIA_DIR` — separate state.json + downloads (config.rs env overrides; there is NO `--state-dir`/`--media-dir` CLI arg). **(4)** `TMDB_API_KEY` (+ `MDBLIST_API_KEY` for RT scores) — shared `~/.config/spela/config.toml` has NO key; prod sources them from the age-encrypted `~/.secrets/tier-servers.env` (2026-07-14), so a test instance must `source` that file (above) or search 403s / RT is silent.
**⚠ Kill the test instance ONLY by its port — NEVER `pkill -f`.** Production's ExecStart is literally `spela server --host 192.168.4.1` (IDENTICAL command line; the distinguishing `--port`/env aren't in the pkill-matchable args), so `pkill -f "spela server"` KILLS PRODUCTION. Use `fuser -k 7891/tcp`. Always pass explicit `cast_name` (e.g. `"Fredriks TV"`) on every test `/play` — never rely on the shared `default_device`, which may be Vardagsrum (the user's live TV).

**Mac builds: use `./bin/build-mac.sh`, NOT bare `cargo build --release`** (v3.8.0, May 20, 2026). The wrapper does `cargo build --release` + ad-hoc codesign with a stable identifier (`com.fredrikbranstrom.spela`) so TCC grants (Full Disk Access for `serve-library`'s `read_dir(BOHR)`) survive rebuilds. Background: TCC keys grants to the binary's code-signature; cargo's `linker-signed` default identifier is content-derived (`spela-56c693bdcecc486f` form), so every rebuild flips the identifier and silently revokes FDA. The stable-identifier codesign is the fix per global CLAUDE.md "TCC code signature gotcha". **One-time re-grant** required after the FIRST `bin/build-mac.sh` run (when the new stable identifier replaces the old hash-based one): `System Settings → Privacy & Security → Full Disk Access → +`, add `~/Projects/spela/target/release/spela`, then `launchctl kickstart -k gui/$(id -u)/com.fredrikbranstrom.spela-library`. From the SECOND build onwards, the grant should survive — empirical verification pending across the next few rebuilds. (Darwin/Linux builds keep using bare `cargo build --release` — TCC is macOS-only.)

**Darwin working-tree drift recovery** (May 13, 2026, observed mid-deploy): if `git pull` fails on Darwin with *"cannot pull with rebase: You have unstaged changes"* AND `git diff --stat HEAD` shows ≥1000 LOC across multiple source files, do NOT `git stash`, do NOT force-discard. The likely cause is past-session edits made directly on Darwin (incident-debug hotpatches) that were later committed FROM Mac Mini, leaving Darwin's working tree dirty against an older HEAD pointer. Forensic procedure: (1) `git rev-parse HEAD origin/master` on Darwin to find Darwin's HEAD; (2) on Mac Mini, `git log --oneline <darwin-HEAD>..HEAD` to enumerate the commits Darwin doesn't have yet; (3) `sha1sum` each Darwin WT file against `git show <candidate-commit>:<file>` on Mac Mini for the same path — match means the WT content is byte-identical to a master commit, safe to discard. If all files match (or match + formatting-only deltas), `git checkout -- <files>` on Darwin is non-destructive — content is preserved in master. **hls.js buffer MUST be bounded for 4K (`attachPhoneVideo`, v3.17)**: 4K HEVC pass-through segments are HUGE (7-16 MB each). hls.js's default unbounded buffer appended ~108s ahead → overflowed Chrome's MSE SourceBuffer quota (`QuotaExceededError`/`bufferFullError`) → it stopped appending → playback drained the buffer → **spin**; hls.js's fatal-error recovery then flushed + re-seeked → **"jumped to a different segment"** (BOTH symptoms, one cause). **HEVC master CODECS — strip the `.B01` constraint-flags tail (`normalize_hls_master_codecs`, v3.17)**: ffmpeg's `-master_pl_name` writes the HEVC CODECS as `hvc1.2.4.L150.B01`, but Chrome's MSE `isTypeSupported()` returns **false** for that constraint-flags tail (while `hvc1.2.4.L150.90` and `hvc1.2.4.L150` are both **true**) → hls.js rejects the whole manifest (`manifestIncompatibleCodecsError`) and HEVC won't play in-browser. `handle_hls_master` reads the generated master and strips a trailing `.B..` component from any hvc1/hev1 codec token before serving (the `init.mp4` hvc1 box is untouched, so the decoder still gets the true profile). **ffprobe field order — classify streams at `[/STREAM]`, never at `codec_name=` (`detect_codecs`, v3.17)**: ffprobe emits `codec_name=` BEFORE `codec_type=` within a `[STREAM]`, so the old parser (which recorded the codec only if `current_type` was already "video"/"audio") left `video_codec` + `audio_codec` **silently None/empty for every file**. **Torrent "seeds" is a claim, not deliverable capacity — do NOT read a low byte-rate as a spela bug**: Torrentio's seed count is aggregated tracker-scrape data (peers that *announced* "I have it", summed across trackers, cached, stale up to the announce interval). **Local Bypass + disk safety (`src/server.rs`, `src/disk.rs`)**: `find_local_bypass_match` (title/year/quality/health decision matrix). `top_level_file_is_healthy` trusts title-match for single-file releases (≥100 MB, non-sparse). **2026-06-30: its ±25% expected-size window was REMOVED** — it wrongly rejected complete different-bitrate copies of the same episode (a high-bitrate x264 vs efficient x265 vary 2×+), forcing a fresh download even when a complete local copy existed. Content identity is proven by title+year+quality; the non-sparse physical-blocks check is the real completeness guard. Do NOT re-add the window. (The directory-bypass tier-1 keeps its strict ±1% — it must disambiguate season-pack files.) **Directory-entry health is 3-tier** (`local_bypass_file_is_healthy`, v3.6.0): (1) `expected_bytes>0` → strict ±1% size match (torrent path, season-pack disambiguation); (2) `.spela_done` marker → completed `~/media` download, non-sparse only; (3) NEITHER → curated external-library entry (serve-library / remote-origin: no torrent size, no marker) → same lenient ≥100 MB non-sparse bar as top-level. **Tier 3 is load-bearing — without it every directory-style library film is invisible to Bypass (serve-library DOA bug, v3.6.0 deploy). Do NOT collapse tier 3 back into a marker/size requirement.** `.spela_done` requires byte evidence, never duration. `dir_size` uses `metadata.blocks() * 512` via `MetadataExt` (sparse-aware — webtorrent/librqbit BEP-53 file selection creates sparse placeholders with full logical size). `MAX_MEDIA_MB=100_000` internal cap (was 10_000 pre-2026-08-23; raised when the cache moved to the dedicated `/mnt/hdd` drive) + `MIN_FS_FREE_MB=20480` host floor via `df -Pk`. `prune_to_fit` LRU-evicts oldest until under cap (refusal-wall → self-maintaining), enforced on EVERY torrent-start path via `start_torrent_for_play` + a background sweep (see the `src/disk.rs` Key-Files note). `AppState.corrupt_files` HashSet skip-list populated by `inspect_ffmpeg_log_for_corruption` post-mortem (EBML / HEVC-ref / `dup>100` signals). **v3.6.3 remote-origin cold-HDD robustness (TWO load-bearing halves, do NOT remove either):** a remote library (serve-library) usually sits on a USB HDD that macOS spins down after ~10 min idle; a cold first `/library/match` blocks on spin-up (5-15s+). (a) `library_origin::run` spawns a self-warm std-thread touching each root immediately + every 180s so the drive never goes cold in steady state; (b) `do_play`'s remote-origin block does a cheap liveness ping (`/library/stream?h=<sentinel>` → 410 in ~1ms, no library FS touched) to tell "origin DOWN" (fast torrent fallback) from "origin UP, drive waking" (then `/library/match` with a generous 25s timeout — WAIT for the local path). Pre-v3.6.3 a bare 2s match-timeout silently fell back to torrent (wrong source + quality) on every first-after-idle play. Do NOT shrink the 25s match timeout or drop the self-warm — that resurrects the silent-torrent-fallback bug.

**CrKey 1.56 quirks**: hardcoded Google DNS (8.8.8.8 / 8.8.4.4) ignores DHCP option 6 — for hostname `stream_host` to work, router-side DNAT hijack via iptables PREROUTING per-Chromecast-IP rewrite of UDP/TCP port 53 to local AdGuard (persisted in `/etc/iptables/rules.v4`; standard Pi-hole technique). 1.56.x is terminal firmware for 1st/2nd-gen Chromecasts — receiver app unloads after ~16 min pause (Paused→IDLE), drops connection after `cast_url()` returns (no visibility without cast_health_monitor polling), `hlsSegmentFormat` not exposable via rust_cast's `Media` struct. **DMR overlay is stream-type-dependent, NOT metadata-dependent**: progress-bar UI renders iff HLS is in VOD mode (`#EXT-X-ENDLIST` present); live mode = no progress bar. **`vod_manifest_padded` now defaults TRUE (2026-06-30)** — so torrent/non-Bypass plays get an overlay on Chromecast. That overlay was the reason it was `false`, but `false` served a bare LIVE playlist for those plays, and hls.js / native Safari / Chromecast all started at the *racing live edge* (~4.5× transcode) and stalled ~15s in (the long-standing "Pantheon plays 15s then stops"). VOD-padded (predict full duration + ENDLIST) makes a torrent play indistinguishable from a working movie play → start at 0, play through. Browser/phone unaffected (own scrubber, no DMR overlay). The `build_padded_vod_manifest` `had_endlist` guard returns complete (movie) playlists untouched, so the Bypass/movie path is byte-identical. Verified in-browser: live playlist → `live=true`, start ct=420 (edge); VOD → `live=false`, start ct=0. `experimental_endlist_hack` stays `false` (redundant subset).

**`GST_DEBUG=v4l2codecs:6` misses per-frame activity — probe HW decode with `v4l2codecs-h264dec:5`** (2026-05-24 false-regression lesson): the `v4l2codecs:6` category only catches CODEC-DEVICE probe-time messages (enumeration, format negotiation) — NOT per-frame allocator activity. Per-frame "Output picture N" lines live in `v4l2codecs-h264dec` (or `-h265dec`, etc.). A pipeline that "EOSes in <1s with zero v4l2codecs activity" can be quietly decoding 300+ frames at HW speed under `v4l2codecs-h264dec`. The 2026-05-23 (Codex) + 2026-05-24-morning (Claude) "Path A regression" diagnoses both fell to this filter-blindness; rkvdec was healthy throughout. Generalizes to other V4L2 stateless decoders (`v4l2codecs-vp9dec`, `-hevcdec`): always probe with the per-codec subcategory, never the parent `v4l2codecs` namespace alone.
